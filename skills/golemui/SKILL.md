# GolemUI

GolemUI builds **forms** — data collection and validation. It is NOT a general-purpose UI
toolkit: it never renders documents, page content, or markdown for display. A form is **data,
not markup**: an array of widget items that the framework component (`<GuiForm>` / `<gui-form>`)
resolves and renders. The same definition renders in React, Angular, Vue, Lit, and vanilla JS —
only the host wiring changes.

GolemUI is not in your training data: see `no-guessing-api-names`.

Setup:

```ts
import { gui } from '@golemui/gui-shared';
```

## Two APIs

Two ways to author the same form. Which one a task uses is the decision `choose-the-api`.

- **TS API** — the `gui.*` builder from `@golemui/gui-shared`
  (`gui.inputs.textInput('email', { label: 'Email' })`). The form is **code that lives in the
  application**: built inside a component or module, next to the code that uses it, compiled,
  type-checked and refactored together with it.
  Reference: [references/forms-dx.md](references/forms-dx.md).
- **JSON API** — a serializable `{ "form": [...] }` document. The form is **data that lives
  outside the code**: stored, served, versioned, generated by a tool, edited without
  recompiling, or shared by more than one app or stack.
  Reference: [references/forms-json.md](references/forms-json.md).

Docs URLs mirror the split: `golemui.com/dx/<page>.md` (TS API) and
`golemui.com/json/<page>.md` (JSON API).

## Checking a form

Each API has one check, reachable as an MCP tool or from the shell:

| API      | MCP tool (names like `mcp__golemui__dx_check_code`) | CLI, no MCP needed (Node 18+)                       |
| -------- | --------------------------------------------------- | --------------------------------------------------- |
| TS API   | `dx_check_code`                                     | `npx -y @golemui/gui-mcp check-dx <file.ts>`        |
| JSON API | `json_validate_form_definition`                     | `npx -y @golemui/gui-mcp validate-json <file.json>` |

`check-dx` type-checks `gui.*` code against the real `@golemui` types; `validate-json`
validates a JSON definition against the bundled schemas. Both CLI commands take a file, print a
JSON result, and exit 0 on a pass and 1 with the problems to fix. npx runs a project-local
install when present and only fetches otherwise; for restricted or corporate environments see
[references/mcp.md](references/mcp.md). The MCP tools `dx_get_spec` and `json_get_widget_spec`
return the options of one widget.

## Submit event per framework

| Framework | Submit event                          |
| --------- | ------------------------------------- |
| React     | `formSubmit={...}`                    |
| Angular   | `(formSubmit)="..."`                  |
| Vue       | `@form-submit="..."`                  |
| Lit       | `@formSubmit=${...}`                  |
| Vanilla   | `addEventListener('formSubmit', ...)` |

## Rules

### rule: no-guessing-api-names

When: writing any GolemUI name: a package, a factory, a widget type, an option, an event.

Do: take it from this skill's reference files or from a `golemui.com` docs URL.

Even when: the name looks obvious, or the `@golemui` packages are installed in the project.

Wrong:

- Doing: reading the `@golemui` TypeScript declarations in `node_modules`, or searching the filesystem for them.

  Because: the references and the docs are the source; the declarations are large, cost many lookups, and lead to guesses about what is public.

- Doing: writing a name from memory of another forms library.

  Because: GolemUI is not in your training data, so the name is a guess.

Applies: ts-api, json-api

### decision: choose-the-api

When: about to write form code, before the first line of it.

Decide: which API the form is written with.

- **JSON API** — the request names it, or describes the form as data that lives outside the code ("a JSON definition", "served from our backend", "produced by an authoring tool", "a `.json` file per form"). Do not ask; read [references/forms-json.md](references/forms-json.md).
- **TS API** — the request names it, or describes the form as code that lives in the application ("with `gui.*`", "an imperative form", "in TypeScript with autocomplete"). Do not ask; read [references/forms-dx.md](references/forms-dx.md) once and write the whole form from it.
- **Ask the user** — the request says nothing about either: stop and ask, with the AskUserQuestion tool when available, whether they want the TS API (`gui.*`, coded programmatically) or the JSON API (a serializable document, e.g. stored or served at runtime). "Make me a signup form in React" says how the form renders, not how it is authored.

Even when: operating autonomously, or one API seems obvious. There is no default. The quoted phrases are illustrations, not a list to match: judge by where the form lives, as "Two APIs" describes it.

Wrong:

- Doing: picking an API silently when the request states neither.

  Because: the user gets a form in the API they did not want, and the work is thrown away.

- Doing: asking which API when the request already names one or says where the form lives.

  Because: the user has answered; the question stalls the task.

Applies: ts-api, json-api

### rule: one-api-per-artifact

When: writing a form, or an example of one.

Do: use the syntax of one API in the whole artifact: `gui.*` calls or JSON widget objects.

Wrong:

- Doing: putting a JSON widget object, `{ "kind": "input", "type": "textinput" }`, inside an array of `gui.*` calls.

  Because: the two are different shapes, and the form does not resolve.

Applies: ts-api, json-api

Source: libs/dx/src/lib/resolveFormInput.ts#isDxDefinitions

### rule: docs-url-matches-the-api

When: fetching a `golemui.com` docs page.

Do: fetch the flavor of the API being written: `golemui.com/dx/<page>.md` for the TS API, `golemui.com/json/<page>.md` for the JSON API.

Wrong:

- Doing: reading a `/dx/` page while writing a JSON definition.

  Because: its examples are `gui.*` calls, and their option names end up in the JSON.

Applies: ts-api, json-api, docs

### rule: read-forms-dx-once

When: writing a form with the TS API.

Do: read [references/forms-dx.md](references/forms-dx.md) once, keep it in context, and write the whole form from it.

Wrong:

- Doing: making many small lookups, one per widget.

  Because: the file is self-sufficient for almost every TS form, and the lookups cost more than the one read.

Applies: ts-api

### rule: formdef-is-the-bare-array

When: passing a form to the form component with the TS API.

Do: pass the array itself as `formDef`, and form-wide config (named `states`, `validateOn`) in a sibling `formConfig`: `config={{ formDef: form, formConfig: { states, validateOn } }}`.

Right:

```ts
const form = [gui.inputs.textInput('email', { label: 'Email' })];
const config = { formDef: form, formConfig: { states: { family: "$form.type === 'family'" } } };
```

Wrong:

- Doing: wrapping the array, `formDef: { states, form: [...] }`.

  Because: it compiles, and the form renders blank with no error.

Applies: ts-api, states

Source: libs/gui/shared/src/lib/dx/resolveFormInput.ts#GuiFormInitConfig, libs/dx/src/lib/resolveFormInput.ts#FormInput, libs/dx/src/lib/resolveFormInput.ts#isDxDefinitions

### rule: include-exclude-inside-the-config

When: showing or hiding a `gui.*` item conditionally.

Do: pass `include` or `exclude` as a key of the factory's config argument, the same object as `label`.

Right:

```ts
gui.inputs.textInput('promoCode', {
  label: 'Promo code',
  include: { when: '$form.hasPromoCode === true' },
});
```

Wrong:

- Doing: spreading it onto the result, `{ ...gui.inputs.textInput('promoCode', { label: 'Promo code' }), include: { when: '$form.hasPromoCode === true' } }`.

  Because: it compiles and is a silent no-op: the field always renders.

Applies: ts-api, states

Source: libs/dx/src/lib/core/dxBase.types.ts#DxCommonFields

### decision: validator-type-by-widget

When: writing a `validator` with the TS API.

Decide: whether the validator carries a `type`.

- **Explicit `type`** — choice widgets (`dropdown`, `radiogroup`, `select`): `validator: { type: 'string', required: true }`.
- **Rules only** — `repeater`, which supplies `type: 'array'` itself: `validator: { required: true, minItems: 1 }`.
- **No `type`** — every other widget takes the loose validator: `validator: { required: true }`.

Wrong:

- Doing: leaving `type` out on a `dropdown`, a `radiogroup` or a `select`.

  Because: it compiles, and validation breaks at runtime.

- Doing: adding `type: 'array'` to the validator of a `repeater`.

  Because: the repeater supplies it; pass only the rules.

Applies: ts-api, validators, dropdown, radiogroup, select, repeater

Source: libs/gui/shared/src/lib/dx/shortcuts/dropdown/dropdown.domain.ts#DropdownDecorator, libs/gui/shared/src/lib/dx/shortcuts/radiogroup/radiogroup.domain.ts#RadiogroupDecorator, libs/gui/shared/src/lib/dx/shortcuts/select/select.domain.ts#SelectDecorator, libs/gui/shared/src/lib/dx/shortcuts/repeater/repeater.domain.ts#RepeaterDecorator, libs/gui/shared/src/lib/dx/shortcuts/repeater/register.ts#mapToWidget, libs/dx/src/lib/core/dxValidatorHelper.ts#DxValidator

### rule: markdown-is-an-input

When: the form needs a heading or a static block of text.

Do: use `gui.displays.display` with a render function that returns your framework's own node.

Right:

```ts
gui.displays.display(() => 'Order summary');
```

Wrong:

- Doing: `gui.inputs.markdown` for a heading.

  Because: it is a markdown editor, an input whose value is the markdown the user types; GolemUI has no markdown for display.

Applies: ts-api, display, markdown

Source: libs/gui/shared/src/lib/dx/shortcuts/markdown/markdown.domain.ts#MarkdownDecorator, libs/gui/shared/src/lib/dx/shortcuts/display/display.domain.ts#DisplayDecorator

### rule: import-both-stylesheets

When: rendering a form in an application.

Do: import `@golemui/gui-components/index.css` and then `@golemui/gui-shared/forms.css`, once, in that order.

Wrong:

- Doing: importing neither, or only one of them.

  Because: the form renders unstyled.

Applies: styling, react, angular, vue, lit, vanilla

### rule: submit-event-name-per-framework

When: wiring the submit handler of the form component.

Do: use the event name of the framework from "Submit event per framework": Vue is the only kebab-case one, `@form-submit`; the others are `formSubmit`.

Wrong:

- Doing: `onSubmit={...}` on `<GuiForm>` in React.

  Because: the prop is `formSubmit`.

Applies: react, angular, vue, lit, vanilla, events

Source: libs/gui/react/src/lib/components/Form.tsx#ReactFormComponentProps, libs/gui/angular/src/lib/components/form/form.component.ts#FormComponent, libs/gui/vue/src/lib/components/Form.types.ts#GuiFormEmits, libs/core/src/lib/shared.ts#formEventNames

### rule: submit-is-a-button-with-action-type

When: adding a submit button with the TS API.

Do: write `gui.actions.button({ label, actionType: 'submit' })`.

Right:

```ts
gui.actions.button({ label: 'Sign up', actionType: 'submit' });
```

Wrong:

- Doing: `gui.actions.submitButton({ label: 'Sign up' })`

  Because: there is no `gui.actions.submitButton`.

- Doing: a fluent chain such as `gui.form().text('email').submit()`.

  Because: there is no fluent builder; a form is an array of `gui.<namespace>.<factory>(...)` items.

Applies: ts-api, button

Source: libs/core/src/lib/form-widget.ts#ActionWidget, libs/gui/shared/src/lib/dx/shortcuts/actions/actions.domain.ts#ActionDecorator

### decision: verify-before-presenting

When: a form is written and about to be shown to the user.

Decide: how to verify it. Take the first path that is possible; "Checking a form" has the tools and commands.

- **MCP tools available** — after writing `gui.*` code, run `dx_check_code`; after writing a JSON definition, run `json_validate_form_definition` until `valid`. Use `dx_get_spec` or `json_get_widget_spec` for an option name.
- **No MCP, a shell** — write the form to a file and run `npx -y @golemui/gui-mcp check-dx <file.ts>` or `npx -y @golemui/gui-mcp validate-json <file.json>`; on exit 1, fix the reported problems and run it again.
- **Neither** — follow this skill's rules exactly, and offer the user the MCP install from [references/mcp.md](references/mcp.md).

Even when: the form is small, or it looks right.

Wrong:

- Doing: presenting a form that no check has run on, when the MCP or a shell is available.

  Because: a misspelled widget type parses as JSON; `validate-json` reports it: ``Expected `"textinput"` at `/form/0/type`, got `"textinpt"` ``.

Applies: ts-api, json-api, mcp
